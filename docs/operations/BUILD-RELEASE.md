## CI quality gates
1. Structural pack schema validator + negative tests.
2. Rust core unit tests / property-based comparator tests.
3. Rust PostgreSQL integration tests (Linux runner with disposable local DB and least-privilege role, never shared production server).
4. TS typecheck/lint/unit tests as scripts become available.
5. Release jobs for selected six assets, signing/notarization secrets managed by GitHub not committed. Validate file existence, unpack/install smoke and native runtime prerequisite.
6. Artifact naming/version/architecture verified from actual builds; no "six platforms supported" claim from just workflow YAML.

## CI branch scope (ADR-029)
`managed-runtime.yml` starts only on pushes to `main` and `release/**` that match its path filter, and on `workflow_dispatch`. It has no `pull_request` trigger: feature branches and pull requests are verified locally before merge, and a feature branch can still be run by hand from the Actions tab. `bash scripts/test_ci_workflow.sh` pins this trigger set.

## Cutting a release
1. Branch `release/vX.Y.Z` from `main`. Pushing it runs CI.
2. Set `X.Y.Z` in `src-tauri/tauri.conf.json` (the release workflow derives the tag from it), `src-tauri/Cargo.toml` and the `tauri-native` entry in `src-tauri/Cargo.lock`. Workspace crates under `crates/` keep their own versions.
3. Add `## [X.Y.Z] - YYYY-MM-DD` at the top of `CHANGELOG.md` with Fixed/Changed/Known limitations, including whether a local PostgreSQL install is required.
4. Run `bash scripts/test_release_version.sh`, `bash scripts/test_ci_workflow.sh` and `bash scripts/test_release_workflow.sh`.
5. Commit, then `git tag -a vX.Y.Z` with the changelog section as the message. Push the branch, then the tag; the tag push runs `release.yml`, which publishes the release only after every platform uploads. Its GitHub notes are generated by `gh release create --generate-notes`; paste the `CHANGELOG.md` section over them if the release page should match.
6. Merge `release/vX.Y.Z` back into `main`.

## PostgreSQL runtime distribution trade-off
Offline app binary is not synonymous with self-contained SQL engine. At P1 local PostgreSQL must be installed or run in a dedicated disposable local container; UI must explain missing runtime. At P4 decide per OS between managed sidecar distributions vs validated external local install; package platform binaries, keep PostgreSQL license notices, maintain safe data dir and service lifecycle, run low-privilege, verify codesigning/port binding. Do NOT bundle arbitrary binaries from untrusted URL in release workflow.

## Pre-release checklist
- [ ] `bun.lock` + `Cargo.lock` committed as appropriate and install frozen.
- [ ] Existing tauri-ui window/theme/debug/external-link/size optimization working.
- [ ] No secrets in code/CI logs; dependency audits triaged for reachable issues.
- [ ] Tauri capability allowlist minimized; filesystem/network access intentional.
- [ ] DB recovery/reset fails closed and user-visible status accurate.
- [ ] Build artifacts validated for all selected architectures, with runtime readiness test and install/uninstall behavior.
- [ ] Release notes clearly specify whether a preinstalled local PostgreSQL is required.

## Linux release and installer

The release workflow publishes a checksum manifest named
`sql-judge-linux-x86_64.SHA256SUMS` alongside the Linux AppImage and DEB.
The installer refuses to continue if the manifest or the matching checksum is
missing or invalid.

Build locally on Linux:

```bash
bun install --frozen-lockfile
bun run tauri build --bundles appimage,deb
```

Artifacts are written below `src-tauri/target/release/bundle/`. Do not commit
that directory. The supported public installation command is:

```bash
curl -fsSL https://raw.githubusercontent.com/vandunxg/sql-judge/main/scripts/install-linux.sh | bash
```

The default `--system` mode uses `sudo`: Debian-family systems install the
verified DEB, while other Linux distributions install the verified AppImage
under `/opt/sql-judge`, add `/usr/local/bin/sql-judge`, and create a desktop
entry. Use `--user` when system-wide installation is not wanted:

```bash
curl -fsSL https://raw.githubusercontent.com/vandunxg/sql-judge/main/scripts/install-linux.sh | bash -s -- --user
```

The user mode installs under `~/.local/bin` and
`~/.local/share/applications` without `sudo`. The first release supports
Linux `x86_64` only; other architectures fail closed. AppImage execution may
still require the distribution's FUSE/AppImage support. SQL Judge is not a
bundled PostgreSQL server: install or configure the required local runtime
separately before judging.

The installer is a convenience wrapper around the GitHub release, not a
replacement for reviewing release provenance. For sensitive environments,
download `scripts/install-linux.sh`, inspect it, and execute the local copy.
